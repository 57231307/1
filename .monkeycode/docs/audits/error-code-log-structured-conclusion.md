# 错误码与日志结构化综合结论

- 审计日期：2026-08-22
- 审计范围：`backend/src/`
- 源报告：
  - 3.12 错误码：`audits/error-code-scan.md`
  - 3.13 日志结构化：`audits/log-structured-scan.md`
- 审计角色：审计代理（只读审计，不修改代码、不创建 PR、不推送）

## 结论

### 结论一：错误码体系规范，硬编码消息建议逐步常量化但不阻塞

- `AppError` 共 10 个 variant，已建立统一的 `error_code`（稳定对外码）、`public_message`（脱敏文案）、HTTP 状态码映射、日志 severity/action 集中维护，分层清晰，体系设计规范。
- handler/service 层 2799 次构造调用中仅 4 次引用 `err_msg::` 常量，常量化覆盖率 <0.1%；硬编码消息总计 2344 处（`format!` 拼接 1543 + 静态字面量 801），存在文案不一致、中英混用、底层错误细节拼入日志等问题。
- **判断**：错误码骨架（variant + error_code + 脱敏机制）已达生产可用水平；硬编码消息属于一致性/可维护性债务，建议按"X 不存在"模板、状态校验、数值校验等高频文案分批提取常量，英文消息中文化，`format!` 拼底层 `e` 的场景统一模板前缀，**不构成发布阻塞项**。

### 结论二：日志结构化程度高，service 层 trace_id 传递需后续补

- 结构化日志调用合计约 1771 处（全限定 779 + 简短 992），非结构化日志 348 处，其中 94%（328 处）集中在 `cli/` 目录，业务代码（service/handler）已基本采用 tracing 宏，结构化程度高。
- 中间件层（`trace_context.rs` / `audit_context.rs` / `omni_audit.rs`）已建立完整的 trace_id 生成、请求头解析、span 注入、响应头回写链路；但 trace_id 在 service 层几乎不携带（0/429），业务日志无法与请求 trace 关联，链路追踪断在业务层。
- 带显式上下文字段的结构化日志比例约 13.7%（243/1771），大量 service 日志使用位置参数格式化而非键值对字段，对结构化采集不友好。
- **判断**：日志体系整体规范，CLI 脚本 println 迁移、service 层 trace_id 补齐（通过 `#[tracing::instrument]` 自动 span 下沉或手工传参）、位置参数改键值对字段三项为后续优化项，**不阻塞当前发布**，建议纳入下一迭代逐步补齐。
