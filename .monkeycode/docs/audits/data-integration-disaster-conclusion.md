## 二、接口集成（28.1-28.7）

报告确认存在，覆盖 7 项扫描（28.2 幂等性未纳入本次综合确认范围，报告内为高风险，详见原报告）：

| 编号 | 扫描项 | 风险等级 | 关键结论 |
|------|--------|----------|----------|
| 28.1 | 第三方鉴权 | 中 | 邮件服务实现阿里云 RPC V1（HMAC-SHA1）与腾讯云 TC3-HMAC-SHA256 双签名，密钥经 `EMAIL_API_KEY` 环境注入；Kafka 鉴权下沉到 `KafkaSettings` 配置层，service 层无可见校验。HMAC-SHA1 受第三方（阿里云 DirectMail RPC V1）签名协议约束 |
| 28.3 | 数据同步 | 中 | 仅单向业务字段同步（质检状态→库存等级/售价、ES 同步），无双向同步、无跨库 `replicate` 抽象；主备切换时备库 catch-up 未完成仍继续切换，存在数据不一致风险 |
| 28.4 | 降级熔断 | 高 | 仅有局部降级（锁中毒、静态资源 fallback、版本降级检查）；`failover_circuit_state` 仅是 Prometheus Gauge 指标，无真实熔断状态机（open/half-open/closed），无自动触发逻辑 |
| 28.5 | Webhook 可靠性 | 高 | 有 retry_count 持久化与上限保护（批次 251）；缺死信队列、缺回调签名校验、缺退避策略（指数退避/抖动）、缺独立 webhook_logs 表、缺异步投递 worker |
| 28.6 | 契约测试 | 高 | 无真正契约测试（tests/ 中 contract 均为业务实体名或 AppError 单测）；无 pact/schemathesis；OpenAPI 覆盖率仅 ~12%（14/115） |
| 28.7 | 故障演练 | 高 | 有 `test_switch` 手动切换 + `wait_for_backup_catchup`；无 chaos 注入、无故障演练编排、无自动 failover 触发、测试覆盖极薄 |

**接口集成小结**：6 项确认项中 1 中风险（28.1）、1 中风险（28.3）、4 高风险（28.4/28.5/28.6/28.7）。接口集成维度整体偏弱，熔断、Webhook 可靠性、契约测试、故障演练四项均为高风险，处于"有指标埋点、无真实机制"的状态。

## 三、灾备运维（29.1-29.6）

报告确认存在，覆盖 6 项扫描：

| 编号 | 扫描项 | 风险等级 | 关键结论 |
|------|--------|----------|----------|
| 29.1 | RTO/RPO 指标 | 高 | RTO/RPO 仅停留在审计报告与技术债清单中，运维文档未落地实际指标定义，无代码/配置定义阈值或自动验证机制 |
| 29.2 | 主备切换实现 | 中 | failover_service 已实现切换计数器与熔断状态追踪，具备观测能力；切换需手动触发，缺连续 N 次健康检查失败自动转移，RPO=0 未在代码层补偿 |
| 29.3 | 异地灾备 | 高 | backend/ 完全无异地灾备/DR 站点/standby 集群相关代码或配置，零命中，当前为单机房部署 |
| 29.4 | 业务降级 | 中 | 降级逻辑零散分布（锁中毒、版本降级），未系统化；缺 read_only 模式、限流降级、统一降级中心 |
| 29.5 | 灾难恢复剧本 | 高 | `.monkeycode/docs/` 下无 disaster/recovery/runbook/dr 任何文档，运维无标准操作剧本 |
| 29.6 | 灾备演练记录 | 高 | 第三方依赖故障、数据库主备切换、定期灾备三项演练全部未完成，无历史演练记录 |

**灾备运维小结**：6 项中 4 高风险、2 中风险。灾备维度存在系统性缺口：单机房部署无异地容灾、RTO/RPO 无量化承诺、无恢复剧本、无演练记录。一旦发生机房级或数据库主库级故障，面临恢复时间不可控、数据丢失量不可控、运维处置无章法三重风险。

## 四、三维交叉风险分析

三个维度存在相互放大风险的传导链：

1. **28.4 降级熔断（高）× 29.2 主备切换（中）**：无真实熔断状态机，主备切换仅手动触发，依赖故障时熔断器无法自动驱动 failover，恢复完全依赖人工介入。
2. **28.5 Webhook 可靠性（高）× 29.6 灾备演练（高）**：Webhook 缺死信队列与退避策略，灾难场景下外部回调丢失无法追溯，且从未演练验证过恢复路径。
3. **28.7 故障演练（高）× 29.6 灾备演练（高）× 29.5 恢复剧本（高）**：三重叠加，故障注入、演练记录、操作剧本全空白，任何灾备承诺均无证据支撑。
4. **27.8 迁移校验（需改进）× 29.1 RTO/RPO（高）**：迁移无后置校验 + RPO 无量化承诺，数据完整性在迁移与灾难两个节点均无验证闭环。
5. **28.1 第三方鉴权（中，HMAC-SHA1 约束）**：HMAC-SHA1 受阿里云 DirectMail RPC V1 签名协议约束，属第三方强制要求，非自主选择，升级需第三方协议演进配合。

## 五、优先级建议汇总

| 28.4 | 无真实熔断状态机 | `failover_service.rs` 实现 CircuitBreaker（open/half-open/closed），驱动 `failover_circuit_state` 指标，从埋点升级为机制 |
| 28.5 | Webhook 缺死信/退避/签名校验 | 引入 `webhook_logs` 表、死信队列、指数退避+抖动、HMAC 回调签名校验、异步投递 worker |

## 六、综合判定

- **数据治理（27.x）**：整体健康，2 优秀 + 5 良好 + 1 需改进，唯一短板为迁移校验。治理底座扎实，可作为其他维度修复的基础。
- **接口集成（28.x）**：整体偏弱，确认的 6 项中 4 项高风险。熔断/Webhook/契约测试/故障演练均处于"有埋点无机制"状态，需从指标观测升级为运行时机制。
- **灾备运维（29.x）**：整体高风险，6 项中 4 项高风险。单机房部署 + 无 RTO/RPO + 无剧本 + 无演练，构成系统性业务连续性缺口。

三个维度的成熟度呈递减趋势：数据治理（良好）→ 接口集成（偏弱）→ 灾备运维（高风险）。数据治理的扎实底座与灾备运维的系统性缺口形成鲜明对比，建议将灾备治理列为 P1 级专项，按"定义指标 → 编写剧本 → 落地自动切换 → 定期演练"路径推进，同时补齐接口集成的熔断与 Webhook 可靠性机制。
